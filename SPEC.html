1. Overview

A static, mobile first recipe website for mostly healthy dishes. Recipes are plain Markdown files with structured frontmatter. Eleventy builds the site into docs/, which GitHub Pages serves for free. No server side logic: search runs on a static index and the weekly planner lives in the browser's local storage.

Site name: Recipe Book (header next to the logo, browser tab, social previews). Language: English (interface and recipes).

Goals

  • Adding a recipe is creating one Markdown file (plus an optional photo).
  • Every recipe can be rescaled to any number of portions in the browser.
  • Fast static search with filters for categories and tags.
  • A weekly dinner planner that persists on the device.
  • Modern, bright, health focused look that works well on a phone in the kitchen.

3. Recipe content model

One file per recipe in src/recipes/. The frontmatter holds all structured data, the Markdown body holds the method.

Recipe URLs

  • The URL comes only from the file name: src/recipes/oat-banana-waffles.md becomes /recipe-book/recipes/oat-banana-waffles/.
  • Categories, tags, title and date are never part of a recipe URL. Adding, removing or renaming a category or tag, or retitling a recipe, doesn't change any recipe URL, so bookmarks, shared links and planner entries keep working.
  • This is enforced in src/recipes/recipes.11tydata.js with a fixed permalink built from page.fileSlug. A permalink in a recipe's own frontmatter fails the build.
  • Category pages (/recipe-book/categories/<slug>/) are separate listing pages. They link to recipes but never contain them in their path.
  • File names: lowercase, words separated by hyphens, English. Renaming a file is the only thing that changes a URL, so avoid it once a recipe is published.

Ingredients

Ingredients are written in YAML block style: one field per line, no curly braces. There are two shapes:

  • Plain list for simple recipes without sections: 
    ingredients:
  - name: red lentils
    amount: 200
    unit: g
  - name: onion
    amount: 1
  • Grouped when the recipe has sections: each key is a group name (shown as a heading, e.g. Batter, To serve) holding a list of items. Groups appear in the order they are written. 
    ingredients:
  Batter:
    - name: rolled oats
      amount: 150
      unit: g
  To serve:
    - name: Greek yoghurt
      amount: 150
      unit: g

The two shapes cannot be mixed within one recipe. The build normalises both into the same internal list (each item gets a group, empty for plain lists), so templates, scaling and the future shopping list only deal with one format.

Ingredient item

Field order doesn't matter, but writing name first is the convention. Quotes are only needed when a value starts with a special YAML character or looks like a number or boolean that should stay text.

FieldTypeRequiredDescription
namestringyesIngredient name, e.g. "rolled oats".
amountnumbernoQuantity for servings.amount portions. Decimals allowed (0.5). Omit for "to taste" items.
unitstringnoMetric only: g, kg, ml, l, tsp, tbsp, pinch, clove, handful, piece, can, ... Always written in the singular; words get a plural on display when the shown amount is more than 1 (½ clove, 1 clove, 1½ cloves, 2 handfuls), abbreviations never change (2 tbsp). Omit for countable items ("2 eggs").
notestringnoPreparation or remark: "finely chopped", "to serve", "optional".
scalebooleanno (default true)Set to false for amounts that should not change with portions (a pinch of salt, 1 bay leaf).

Unknown fields in an item (for example a typo like ammount) fail the build with the file name, the ingredient and the list of allowed fields.

Body (method)

  • Free Markdown. Convention: a numbered list of steps, optionally followed by a ## Tips section.
  • No headings needed for ingredients: those are rendered from the frontmatter.
  • A recipe whose method hasn't been written yet may say so in one line. It still builds; the build info lists it next to the recipes without photos, as a reminder.

Validation

The build fails with a clear message (file name + missing field) when a required field is missing or has the wrong type, or when a category or tag is not in the fixed list (see Categories and tags for the message format). This keeps broken recipes out of the published site.

4. Categories and tags

Decision: both categories and tags come from fixed lists in one definition file. Using a term that isn't listed stops the build with a descriptive error.

Roles

  • Categories say what kind of dish it is. Use one or two per recipe. Each category gets a listing page, a home page tile, an accent colour and a placeholder illustration.
  • Tags describe properties of the dish, and a recipe can have several. They are organised in groups, and each group becomes one filter on the search page.

Definition file

src/_data/taxonomy.js is the single source of truth. Eleventy exposes it to all templates as taxonomy, and the recipe validation reads the same file.

Term fields

List order is display order: category tiles and filter chips follow the order in the file.

Colours in the layout

  • From each term's color the build derives three shades: accent (the colour itself), tint (a very light mix with white, used for badge backgrounds and tile surfaces) and ink (a dark mix, used for badge text). This keeps badges readable without defining three colours per term.
  • Every derived ink/tint pair is checked for WCAG AA contrast (4.5:1) at build time. A failing pair gives a warning that names the term and suggests a darker colour.
  • Eleventy generates taxonomy.css with one class per term, which sets custom properties: 
    .cat-breakfast { --accent: #F6B73C; --tint: #FEF6E4; --ink: #6B4A07; }
.tag-vegan     { --accent: #2F9E6E; --tint: #E3F5EC; --ink: #16513A; }
    Two more shades are derived for filled buttons and category chips: solid (the accent darkened just enough for white text at AA, or lightened for dark text in dark mode) and on-solid (that text colour). Every value is a CSS light-dark() pair, so one class covers both themes. Components only use var(--accent), var(--tint), var(--ink), var(--solid) and var(--on-solid). A badge, a card's top border, a category tile or the recipe header stripe gets its colour just by adding the term class.
  • The recipe page uses its first category's class, so the accent colour runs through the whole page (header stripe, portion counter, "Add to planner" button).

Matching rules

  • Matching is case-insensitive and ignores surrounding spaces, so Vegan and vegan are the same term. Pages always show the name as written in the definition file.
  • Anything else must match exactly (no automatic plurals or synonyms), but the error suggests the closest match.
  • The same term listed twice in a recipe gives an error. So does a duplicate name or slug in the definition file.

Error message

Validation runs once over all recipes at the start of the build. It collects every problem, prints them grouped per file and then exits with a non-zero code, so a single build shows all mistakes. During npm run serve the errors are printed and the dev server keeps watching, so fixing the file triggers a rebuild.

Each unknown term produces a message like this:

5. Example recipe

src/recipes/oat-banana-waffles.md

---
title: Oat & Banana Waffles
description: Naturally sweet waffles with oats, banana and a hint of cinnamon.
date: 2026-09-26
categories: [Breakfast, Baking]
tags: [vegetarian, freezer-friendly, kid-friendly]
image: oat-banana-waffles.jpg
servings:
  amount: 7
  unit: waffles
  unitSingular: waffle
  note: Might vary depending on the size of your waffle iron.
ingredients:
  Batter:
    - name: rolled oats
      amount: 150
      unit: g
      note: blended into flour
    - name: ripe bananas
      amount: 2
    - name: eggs
      amount: 2
    - name: milk
      amount: 250
      unit: ml
      note: or a plant based drink
    - name: baking powder
      amount: 1
      unit: tsp
    - name: ground cinnamon
      amount: 1
      unit: tsp
    - name: salt
      amount: 1
      unit: pinch
      scale: false
  To serve:
    - name: Greek yoghurt
      amount: 150
      unit: g
    - name: fresh berries
      amount: 100
      unit: g
    - name: maple syrup
      note: optional, to taste
---

1. Blend the oats into a fine flour.
2. Add the bananas, eggs, milk, baking powder, cinnamon and salt and blend until smooth.
3. Let the batter rest for 10 minutes so the oats can absorb the liquid.
4. Preheat and lightly grease the waffle iron.
5. Bake each waffle for 4 to 5 minutes until golden and crisp.
6. Serve with yoghurt, berries and a drizzle of maple syrup.

## Tips

- Waffles freeze well; reheat them in the toaster.

6. Portion scaling

  • The recipe page shows a spin counter: [ − ] 7 waffles [ + ], with the servings.note as a small byline underneath.
  • Input is an integer, minimum 1, maximum 99. The number can also be typed. Unit label switches between singular and plural.
  • On change, every ingredient with an amount and scale not false is recalculated: new = amount × chosen / servings.amount. Updates happen instantly without reloading.
  • The server rendered page shows the original amounts, so the recipe is readable without JavaScript. The script enhances it (progressive enhancement). Base amounts are stored in data- attributes.
  • A "reset" link returns to the original number when it differs.
  • The chosen number is reflected in the URL (?portions=4) so a scaled recipe can be shared or bookmarked.

Number formatting

CaseRuleExample
g, ml at 100 or moreround to nearest 5214 g → 215 g
g, ml below 100round to whole number42.9 g → 43 g
g, ml reaching 1000 or moreswitch to kg / l, max 2 decimals, trailing zeros removed1250 g → 1.25 kg, 2000 ml → 2 l
kg, l dropping below 1switch to g / ml and apply the g/ml rules0.25 kg → 250 g
Units without fixed size (tsp, tbsp, pieces, no unit)round to nearest ¼ and show as fraction1.33 tsp → 1¼ tsp, 2.5 eggs → 2½ eggs
Result would be 0show the smallest step instead¼ tsp

Unit switching: amounts in g/kg and ml/l are converted to the base unit (g, ml) after scaling, rounded, and then shown in kg or l when they reach 1000. This works in both directions, so a recipe written in kg shows grams when scaled down. Other units (tsp, tbsp, pinch, pieces, ...) are never converted. The same logic will be reused to add up amounts in the future shopping list.

8. Search

Decision: Pagefind (pagefind npm package, v1.x).
  • Runs after Eleventy: eleventy && pagefind --site docs. The index is written to docs/pagefind/ and committed together with the site.
  • Only recipe pages are indexed: the recipe <article> gets data-pagefind-body. Title, ingredients and method are all searchable, so searching "lentils" finds recipes that use lentils.
  • Filters: each category rendered with data-pagefind-filter="category", each tag with its group as the filter name (e.g. data-pagefind-filter="Diet"), so every tag group shows up as its own filter.
  • Metadata for result cards: data-pagefind-meta="image", plus the title and description.
  • UI: our own UI on the Pagefind JavaScript API (search.js), not the Component UI. The Component UI was tried first but is 175 KB of script and can't render results as our recipe cards; the planner's dish picker needs the JavaScript API anyway. Results are rendered from a small recipe list embedded in the page (title, thumbnail, category, tags, servings), with Pagefind's excerpt (matched words highlighted) under the title. The home page search box submits to /search/?q=….
  • Filters: on phones a "Filters" button (with a count badge) opens a bottom sheet with one chip group per filter and a "Show N recipes" button; on desktop the same groups form a sidebar. Active filters show as removable chips above the results. Within a group values are OR-ed, across groups AND-ed. Counts are real facet counts (each group counted without its own selection) and values that would give no results are hidden.
  • All search state is in the URL (?q=lentils&diet=vegan&category=soup, one parameter per group slug), so tag chips on recipe pages link straight to a filtered search.
  • An empty search lists all recipes. If the index can't be loaded, a notice appears and titles and descriptions are searched in the browser instead.
  • The planner's dish picker reuses the same index through the Pagefind JavaScript API (pagefind.search()), so there is one search engine for the whole site.
  • Search does not work with npm run serve alone until the index has been built once; a serve script that builds the index first is part of the setup.

9. Weekly planner

Decisions: one dinner per day, real calendar weeks starting on Monday, stored in localStorage.

Planner page

  • Shows one week (Mon to Sun) with dates. Arrows to go to previous and next week, and a "This week" button. Today is highlighted.
  • Mobile and tablet: vertical list of 7 day rows. From 1024px: 7 column grid.
  • Filled day: thumbnail, dish name (links to the recipe with ?portions= set), portion count, remove button.
  • Empty day: "+ Add dinner" opens the dish picker (search field with live Pagefind results).

Adding a dish

From a recipe page ("Add to planner") or from the planner's dish picker, a dialog asks:

  1. Portions: spin counter, prefilled with the number currently chosen on the recipe page (or the recipe's default).
  2. Days: the 7 days of the selected week as toggle chips, with week navigation inside the dialog. Multiple days can be selected, because a dish is often eaten on several (usually consecutive) days.
  3. Days that already have a dish show its name; selecting them asks for confirmation to replace.

The portions are stored per day entry, so leftovers on day two can have a different count.

Interaction details (phone first)

  • One sheet for adding: on phones every dialog is a bottom sheet (drag the handle down, tap outside or press Escape to close); from 640px it is a centred dialog. The planner's "+ Add dinner" opens the dish picker view ("Dinner for Tue 29 Sept"): search field, "Recently planned" dishes, then all recipes A to Z. Typing searches live with Pagefind. On phones the field is not focused automatically, so the keyboard doesn't hide the list.
  • Picking a dish moves to the plan view in the same sheet (with a back arrow): portions stepper (defaults to the recipe's servings) and the days of the week, with the tapped day already selected. So planning one dinner is three taps: + Add dinner, the dish, Add.
  • Days are a list of toggle rows (not small chips) so each row can show the date and what is planned: "Free", the current dish, or "Already planned" when it is this dish. Tapping a day that has another dish shows an inline confirmation under it ("Replace Quick Bread on Tue 29 Sept?" Keep it / Replace); a confirmed day is marked "Replaces …". Selections survive week navigation inside the sheet.
  • The save button says what happens: "Pick one or more days" (disabled), "Add to Tue 29 Sept", "Add to 3 days".
  • Every change (add, replace, remove) shows a toast with Undo instead of asking for confirmation first.
  • Filled day row: thumbnail and title link to the recipe with ?portions=; a portions chip ("4 servings") opens a small day sheet with a portions stepper (saved immediately), "Change dish" and "Remove"; the × button removes directly (with Undo).
  • Week navigation: arrows in a sticky week bar ("This week", "Next week", "In 3 weeks"… with the date range), swipe sideways over the days, or the arrow keys on a keyboard. A "This week" button appears when another week is shown. The shown week is kept in the URL (?week=2026-09-28). Newly added days briefly highlight.
  • Steppers: tap − / +, hold to repeat faster, or type the number. 48px round buttons.
  • Changes made in another tab show up immediately (the storage event).

Storage format

Key recipeBook.planner.v1. Entries are keyed by ISO date. Title and image are copied in so the planner renders without loading recipe pages. The stored image is the smallest generated photo (400px WebP) or, without a photo, the placeholder SVG.

{
  "version": 1,
  "days": {
    "2026-09-28": { "slug": "oat-banana-waffles", "title": "Oat & Banana Waffles",
                    "image": "/recipe-book/assets/images/recipes/oat-banana-waffles.jpg", "portions": 4 },
    "2026-09-29": { "slug": "oat-banana-waffles", "title": "Oat & Banana Waffles",
                    "image": "/recipe-book/assets/images/recipes/oat-banana-waffles.jpg", "portions": 2 }
  }
}
  • All reads and writes go through one small module that catches storage errors (private browsing, storage full) and shows a notice instead of breaking the page.
  • The version field allows migrating the format later.
  • History: the planner keeps the current week, all future weeks, and the 8 previous weeks. On every load, entries dated before the Monday 8 weeks before the current week are removed. Week navigation stops at the oldest kept week.
  • If a recipe was renamed or removed, the entry still shows its stored title; the link leads to the 404 page with search.

10. Design and layout

Principles

  • Mobile first: base CSS targets ~360px wide phones; breakpoints at 640px (tablet) and 1024px (desktop). No horizontal scrolling of the page (the "Recently added" row on phones scrolls sideways on its own).
  • Bright and fresh: lots of white space, warm off white background, leafy green as the main colour, citrus and berry accents taken from fruit and vegetables.
  • Large touch targets (min 44px), readable 17px base text for use while cooking.
  • Rounded cards (16px radius), soft shadows, generous photos.
  • Accessible: WCAG AA contrast, visible focus states, respects prefers-reduced-motion.

Light and dark mode

  • Three settings: System (default, follows the device through prefers-color-scheme), Light and Dark.
  • Subtle toggle: not in the header or bottom bar. It sits in the site footer as a small, low contrast control ("Mode:" followed by a single icon button: monitor for System, sun for Light, moon for Dark; each click cycles System → Light → Dark, and the tooltip names the current and next mode). It is reachable on every page but never draws attention.
  • The choice is stored in localStorage under recipeBook.theme ("system", "light" or "dark"). If storage is unavailable, the site follows the system setting.
  • A tiny inline script in <head> reads the setting and sets data-theme on <html> before the page renders, so there is no flash of the wrong theme. It also adds a js class, so controls that need JavaScript (steppers, "Add to planner") are hidden without it.
  • Colours are CSS light-dark() pairs; data-theme only sets color-scheme (light dark for System), so every colour is defined once.
  • All colours are CSS custom properties with a dark set, for example:
    TokenLightDark
    background#FBFAF5 cream#121814 deep green black
    surface (cards)#FFFFFF#1B231E
    text#1F2A24 ink#E6EEE8
    primary#2F9E6E leaf#4CC08C lighter leaf
    muted text#5D6B63#9AABA1
  • Category and tag colours: the build generates a dark variant of each term's tint and ink (tint = accent mixed into the dark surface, ink = accent mixed with white) and checks AA contrast for both themes.
  • Illustrations keep their own light backgrounds (they sit in rounded frames, like pictures). In dark mode they get a slight dim (filter: brightness(.9)) so they don't glare. Dedicated dark artwork is in the backlog if this looks off.

Typography

Decision: Nunito for everything (rounded, friendly, one family).
  • Weights: 400 (body), 700 (subheadings, ingredient amounts, buttons), 800 (page titles). Headings get slightly tighter letter spacing (-0.01em).
  • Ingredient amounts use tabular numbers (font-variant-numeric: tabular-nums) so they line up and don't jump while the portion counter changes.
  • Self hosted with the @fontsource/nunito npm package (WOFF2, font-display: swap), copied into the build: no requests to Google, works offline. The latin 400, 700 and 800 files are preloaded, so text never swaps from the fallback after the first paint (a late 700 made the nav labels change width and the nav buttons shift).
  • Subsets: latin and latin-ext, because recipe names contain characters like ę, ł, ż (Kruche ciasto na tartę).
  • Fallback stack: Nunito, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif.
  • Base size 17px on phones, line height 1.6 for body text, max line length about 70 characters on wide screens.

11. Images and artwork

  • No photos exist yet; every recipe starts with its category placeholder. Photos are added over time.
  • One folder per recipe: src/assets/images/recipes/<slug>/. The main photo is named by image, extra photos by gallery. Example: 
    image: sponge-cake.jpg
imagePosition: center 40%
gallery:
  - file: whisked-whites.jpg
    caption: Egg whites whisked to stiff peaks
  - file: slice.jpg
  • The main photo is used as header (16:9 crop) and card thumbnail (4:3 crop) with CSS object-fit: cover and imagePosition as object-position. Phone photos in any orientation work.
  • Gallery: shown as a row of small square thumbnails below the method. Tapping one opens a full screen viewer (native <dialog> with CSS scroll snap, swipe or arrow keys to move, caption underneath). No gallery library. Without JavaScript the thumbnails link to the full image.
  • Responsive sizes (WebP, widths 400 / 800 / 1600) are generated at build time with @11ty/eleventy-img, lazy loaded except the header image.
  • Validation: a missing photo file fails the build with the recipe, the field and the folder it looked in.

Photo originals

  • Originals are committed in the repository, but pre-shrunk so the repository stays well under the GitHub Pages 1 GB limit.
  • scripts/shrink_photos.py (Python, Pillow) processes every photo in src/assets/images/recipes/: longest side capped at 2000 px, JPEG quality 85 (typically 300 to 500 KB), rotation from EXIF applied, and all EXIF metadata removed (including GPS location from phone photos). Already shrunk files are left alone, so it is safe to run repeatedly.
  • Workflow: drop phone photos in the recipe folder, run npm run photos (calls the script), commit.

Placeholder artwork for recipes without a photo

Every recipe shows an image on its card and page header. When a recipe has no image yet, it shows the illustration of its first category. If that category has no illustration file, it falls back to plate.svg. The fallback is resolved at build time, so templates always receive an image path.

Deliberately not photographic. Placeholders are flat vector illustrations, so they can never be mistaken for a real photo of the dish:

  • Flat shapes only: no gradients, textures, realistic shading or drop shadows (only a soft flat ellipse under the object).
  • Background is the category's light tint with a large soft circle in a mid shade, a few scattered dots and two small corner leaves. This frame is the same on every placeholder, so they read as one set.
  • Colours come only from the taxonomy palette (the category colour plus fixed food colours like berry, citrus and leaf).
  • Canvas is 400 × 300 (4:3, card thumbnail). The subject stays inside the central 16:9 band, so the page header crop keeps it intact.
  • SVG with a <title> and aria-label, a few KB each, crisp at every size.

On the recipe page, a placeholder header also gets a small "No photo yet" chip. The build prints (as info, not an error) a list of recipes that still need a photo.

13. Build and deploy

CommandDoes
npm run buildClean docs/, run Eleventy, run Pagefind on docs/.
npm run photosShrink new photos and strip their metadata (scripts/shrink_photos.py).
npm run serveBuild the search index once, then Eleventy dev server with live reload on port 8080.
  • Deploy: commit the rebuilt docs/ and push to main. GitHub Pages is set to "Deploy from a branch", main, /docs.
  • Public URL: https://monikasuchoszek.github.io/recipe-book/. Eleventy's pathPrefix is "/recipe-book/" and site.url in src/_data/site.js is the full URL (used for canonical links and social previews).
  • All internal links and asset paths go through Eleventy's url filter (HTML Base plugin), so no hardcoded / paths. The planner and search scripts get the prefix from a data-base attribute on <html>.
  • GitHub setup: a project site on the default GitHub Pages domain of the MonikaSuchoszek account, so the repository must be named recipe-book (the folder name locally doesn't matter). No custom domain and no CNAME file.
  • npm run serve also serves under /recipe-book/ locally, so prefix bugs show up during development.
